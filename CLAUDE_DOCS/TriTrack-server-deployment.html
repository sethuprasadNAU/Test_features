TriTrack server — what it takes to stand one up

One Linux host · Docker Compose · seven containers · two inbound ports, 443 and 80 · for the engineer doing the install

This is the companion to TriTrack-server-architecture.html, which answers “is this safe on our network?” This one answers “what do I install, what do I need from Michael, and how do I know it worked?”

Read this before scheduling the work

Sign-in needs a mail relay, and that is a decision for NAU. TriTrack authenticates by emailing a one-time link. The code that sends it is built and tested against a local relay; what it does not have is a relay to send through. A production server refuses to start until one is configured, deliberately — the alternative was a server that accepted every sign-in request, answered 202, and delivered nothing.

What is needed: which relay (hostname and port), from what sending address, whether it needs a username and password, and whether NAU will relay mail for a research service. Any relay works — a campus relay or a commercial sending service. Settle it in the same conversation as the host. A server can be stood up and checked without it; people just cannot log in until it is in place, and one test message to a real inbox is how you know it is.

What you are installing

The same diagram as TriTrack-server-architecture.html, drawn from the compose files. Ports, images and the private network below are what those files actually say.

A Dart web service and a PostgreSQL database, run by Docker Compose behind a Caddy reverse proxy that gets and renews its own TLS certificate. The only outbound connection the application makes is to a mail relay, to send sign-in links. No LDAP, no SSO, no campus storage, no external database.

ContainerImageHost portsWhat it does
proxycaddy:2-alpine443, 80 Terminates TLS and obtains its own certificate. Port 80 serves the ACME challenge only. The single entry point.
serverDart on debian-slimnone The application: sign-in, sync, project membership. The compose file removes its host port explicitly.
postgrespostgres:16-alpinenone The database. No host port in any configuration, so nothing on the network reaches it.
audit-retentionsame as servernone Deletes expired log rows on a timer. A year for sign-in events, 180 days for sync traffic, 30 days for decided join requests.
backup-scheduleron postgres:16-alpinenone One encrypted, signed database dump every 24 hours into a directory on the host disk.
project-destructionsame as servernone Destroys a project on the date its owner scheduled, so no device has to be online for the deletion to happen.
tombstone-retentionsame as servernone Purges records deleted more than 24 months ago, measured from when this server accepted the delete, so the database does not grow without bound.

A seventh service, backup, sits behind a Compose profile and runs on demand. It is not a running container.

What the host needs

  • Linux with Docker Engine and the Compose plugin. No other runtime, no language toolchain, no web server. The images are built on the host from this repository.
  • A publicly resolvable DNS name pointing at the host, and inbound 443 and 80 open to the internet. Port 80 is used only by Let’s Encrypt to answer the certificate challenge. If 80 cannot be opened, say so early: Caddy needs a different challenge method and that changes the configuration.
  • Outbound 443, so the proxy can renew its certificate roughly every 60 days.
  • Outbound to the mail relay — port 587 with STARTTLS by default, or 465 if the relay only speaks TLS from the first byte. The server checks the relay at every start and writes the result to its log, and docker compose run --rm --no-deps server --send-test-email you@nau.edu sends one test message so you can watch it arrive.
  • Disk for the database and for backups. Field records are small: coordinates, timestamps and radio frequencies. Tens of gigabytes is plenty.
  • A regular user account to own the deployment. The containers do not need root, and the backup directory and signing key belong to that user.

What Michael provides

  • The repository, and a walk through .env with you.
  • The backup signing key and the age recipients the dumps are encrypted to. These are secrets; they are generated on the host and never committed.
  • An origin certificate for the server container. This is a second, separate certificate from the public one, generated once on the host with openssl. It authenticates nothing to the proxy; its only job is to satisfy the application’s own refusal to speak cleartext outside loopback. server/README.md has the exact command.

The install, in the order it happens

  1. Clone the repository onto the host as the deployment user.
  2. Write .env from .env.example. The values that matter for a real deployment are the Postgres credentials, TRITRACK_ENV=production, TRITRACK_TLS_DOMAIN (the public name), the two origin-certificate paths, and the backup directory, recipients and signing key.
  3. Generate the origin certificate outside the repository tree, per server/README.md.
  4. Bring the stack up with the TLS overlay: 
    docker compose -f docker-compose.yml -f docker-compose.tls.yml up --build -d
    The overlay sets TRITRACK_ENV=production for you and removes the application’s host port, so the proxy is the only way in.
  5. Watch Caddy get its certificate. First start reaches Let’s Encrypt over port 80. If that port is closed, this is where it stops.

How you know it worked

One command reports the state of the deployment:

scripts/operator_status.sh

It asks the three questions an operator would otherwise have to remember separately, and prints one report. Run it after the first start and after any change.

CheckWhat it tells you
/healthThe process is up. It does not mean the database is reachable.
/readyThe service can actually serve. This is the one to watch.
scripts/verify_tls_termination.sh Brings the TLS overlay up under a throwaway project, checks termination, and tears itself down. It never touches a real deployment’s data.
scripts/backup_status.shWhether a recent backup exists and is signed.

/health and /ready answering differently is the normal way this service tells you the database is gone. A container that is up and not ready is the expected shape of that failure, not a bug.

Questions for NAU, worth settling while you are in the room

  1. Mail relay. See the box at the top. Which relay and port, which sending address, whether it needs credentials, and will NAU relay for this service? Nothing else blocks people logging in.
  2. Where a second copy of the backup lives. Encrypted, signed dumps are written to the host disk every 24 hours and no copy leaves that host today. A backup that only exists on the machine it protects is not a backup. This is an open question, not an oversight.
  3. Who holds the signing and encryption keys, and what happens when the person holding them leaves.
  4. Whether port 80 can be open for the certificate challenge.
  5. Patching and restarts. The stack survives a reboot if Docker starts on boot. Who applies host updates, and on what schedule.

What you do not need to worry about

  • Scale. Teams are small and sync in bursts when devices come back into signal. This is a low-traffic service. One modest VM is the right size.
  • Campus integration. There is none, by design, and adding some is not pending.
  • Student or health data. The records are researchers’ names and email addresses, and the coordinates, times and radio frequencies of collared animals. Sensitive in a conservation sense, because they locate protected species. Not FERPA, not HIPAA, no payment data.
