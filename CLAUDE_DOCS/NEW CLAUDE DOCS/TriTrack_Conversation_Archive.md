## 1. Project Summary

Tri Track is a cross-platform Flutter app (iOS, Android, macOS as a secondary target) built for wildlife field researchers performing VHF radio telemetry — logging directional bearings and non-detections on tagged animals, triangulating estimated tag positions using the Lenth (1981) maximum-likelihood method, planning fieldwork using offline terrain viewshed prediction, and managing project/team data entirely offline-first with backup/restore and CSV export. It originated as a personal/academic project associated with Northern Arizona University wildlife research work.

The project was developed through an iterative design conversation across two AI models (Sonnet for initial design and drafting, Opus for critical review and algorithm-sensitive work), validated against the primary literature (Lenth 1981; NOAA World Magnetic Model), and is being implemented via Claude Code using Flutter/Dart with Riverpod state management and a local SQLite database designed from the outset to support future multi-device sync.

- **SMART/CyberTracker (Painted Dog Conservation) interoperability via webhook** — one-directional (SMART → Tri Track) ingestion is technically feasible via CyberTracker's outbound webhook mechanism, contingent on Tri Track having a Phase 3 server. No inbound path exists for Tri Track → SMART without a manual, organization-configured custom SMART data model.
- **ITM (Longley-Rice) relative-detection-likelihood layer** — technically sound concept (path loss without needing known transmitter power), open-source public-domain reference implementation exists (NTIA/itm), but substantially heavier computation than the binary viewshed and no ready-made Flutter/Dart package exists. Assessed as unlikely to be a clean "one-shot" AI-assisted implementation; would need iterative validation against NTIA's reference test vectors, most plausibly via a Dart FFI wrapper around the existing validated C++ implementation rather than a from-scratch port.

## 7. Candidate Elements for Invention Disclosure Consideration

*(Compiled from the conversation for Cowork's reference when drafting; not a legal determination of patentability or novelty.)*

- The dual magnetic-needle/true-north-arrow live compass display method, with declination shown as the visual offset between two simultaneously rendered, shape-and-label-differentiated indicators (as opposed to a single needle plus a numeric declination readout).
- The field triangulation workflow combining: tag-first observation filtering, a "triangulation session" grouping construct to guard against fusing bearings from a moved animal, and explicit degenerate-geometry detection/guarding around the Lenth MLE (N=1, near-parallel, coincident-observer, near-singular, high-GDOP cases) with user-facing plain-language explanations of *why* an estimate is unreliable.
- The angular range-capture bearing method (Start/End sweep → circular-statistics midpoint and half-range as bearing and uncertainty) as an alternative/adjunct to single-point compass bearing capture, with required correct circular (not linear) handling across the 0°/360° boundary.
- The offline-first, multi-device data model designed for eventual conflict-free merge (soft-delete-only, revision counters, email-anchored cross-device identity, UUID keys) purpose-built for a team of field researchers who sync opportunistically rather than continuously.
- The combination of binary line-of-sight viewshed with a configurable maximum-detection-range clip, and the proposed extension to a power-independent relative-detection-likelihood surface (ITM/Longley-Rice) calibratable against the app's own recorded detection/non-detection field data over time.
- The versioned, structured (vs. free-text) offline observation-sharing payload designed for peer-to-peer exchange over ordinary messaging apps without a server.

### Localization Algorithm: Lenth Maximum Likelihood Estimator

**Reference**
- Lenth, R.V. (1981). "On Finding the Source of a Signal." Technometrics, 23(2), 149-154.
- Validation data available in the 1981 paper; use to unit test implementation
- R packages `radiotrack` and `sigloc` provide reference implementations—consult for validation

**Concept**
Given N observations from known observer positions, each with a bearing and bearing uncertainty, compute the most likely tag position and confidence ellipse.

**Data Input**
Each observation provides:
- Observer location (lat, lon)
- True north bearing (theta, 0-360°)
- Bearing uncertainty (sigma, degrees)

**Algorithm Outline** (Claude Code to research and implement from Lenth 1981)
1. Each bearing defines a ray (line) extending from the observer position at angle theta
2. Compute the point (tag_lat, tag_lon) that minimizes the weighted sum of squared perpendicular distances from that point to each bearing ray
3. Weight by bearing uncertainty: higher certainty (lower sigma) gets higher weight
4. Use iterative optimization (gradient descent or similar) to find the minimum
5. Compute Hessian matrix (second derivatives) at the solution to extract covariance matrix
6. Decompose covariance into uncertainty ellipse: semi-major axis, semi-minor axis, rotation angle

**Output**
- Best-fit tag position (latitude, longitude)
- Uncertainty ellipse (semi-major, semi-minor, rotation)
- Covariance matrix (if needed for downstream analysis)

**Additional Calculations**
- Pairwise intersections: for each pair of observations, solve the two-line intersection algebraically (where do two rays cross?); store as separate layer for visualization
- Users can toggle individual observations on/off to see how each pair contributes

**Testing**
- Use example data from Lenth 1981 paper to validate solver
- Compare output positions and uncertainty ellipses against known correct answers
- Create unit tests that verify Lenth solver against paper examples

### Viewshed Calculation

**Concept**
From a user-selected point on the map, determine which terrain cells are visible (line-of-sight, no terrain obstruction) given a digital elevation model (DEM).

**Data Input**
- Observer position (lat, lon)
- Observer height above ground (altitude AGL, default 1.7m for handheld antenna)
- DEM raster (pre-downloaded)
- Search radius (suggested 5-10 km for Phase One)

**Resolution**
- Coarse grid spacing (10-50 meters) acceptable; fine resolution not necessary
- Signal propagation doesn't differ significantly over 10-50 meter scales
- Coarser = faster computation

**Algorithm Outline**
1. For each grid cell within search radius, compute line-of-sight from observer to that cell
2. Trace line (e.g., Bresenham) from observer through DEM
3. If line clears all intervening terrain, cell is visible; otherwise not
4. Store results as visibility raster or polygon boundary
5. Display on map as overlay (e.g., tinted region, heat map, or boundary line)

**Implementation Options**
- Use GDAL if full GIS capability needed (heavier)
- Write simpler 2D line-of-sight check if performance better
- Pre-compute at coarse resolution; interpolate if needed

**UI Integration**
- Automatic viewshed: when user opens map, compute and display viewshed from current location
- Predict viewshed: user taps "predict viewshed" button, then taps any point on map, app computes and displays that viewshed
- Allow toggling viewshed on/off
- Display as semi-transparent overlay so map remains visible beneath

**Phase Two Enhancement** (not Phase One)
- Optimize viewshed along roads
- Suggest next locations to maximize coverage or reduce position uncertainty
- Rank candidate positions by value
