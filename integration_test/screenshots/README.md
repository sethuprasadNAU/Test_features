# The screenshot harness

Every screenshot on the TriTrack website is generated by this directory. **None
is taken by hand, and none may be** — a hand-taken screenshot cannot be
regenerated, so it starts rotting the moment a screen changes and no check can
tell. **If an image cannot be rebuilt by the command below, it does not go on
the site.**

```
integration_test/screenshots/regenerate.sh                 # every profile
integration_test/screenshots/regenerate.sh iphone-6.9      # one profile
integration_test/screenshots/regenerate.sh iphone-6.9 --accept
```

The committed images live in `website/static/screens/<profile>/`. There is
exactly one copy of each in the repository, so there is nothing for a second
copy to drift from.

---

## What it does, in order

0. **Runs `preflight.dart`, which asks whether this harness is still measuring
   the app** (`/w-10`). It reads the harness's own source and refuses the run
   if a `ProviderContainer` here is built without the app's retry policy. See
   "A harness must be assembled from the app's configuration" below for what
   that cost. It runs before the lock and before any simulator boots, because
   there is no point spending twenty minutes photographing screens with an
   instrument waiting on a rule the app does not have.
1. **Takes a lock on `build/screenshots`, and refuses to start if another run
   holds it.** See "One run at a time" below. A run that cannot take the lock
   exits 2 and names the process that has it.
2. Boots the named simulator **and opens the Simulator application.** Not
   optional: a simulator that is booted but has no window never drives a
   display link, so Flutter renders no frames at all, the driver extension
   never registers, and `flutter drive` waits a quarter of an hour before
   reporting that your app is probably missing an import. That was two of the
   first three runs.
3. `xcrun simctl location set` to the invented study area, so anything asking
   the operating system where it is gets the same answer the seeded data
   assumes.
4. Runs `capture_test.dart` under `flutter drive`. It opens a fresh database,
   fills it from `seed.dart`, boots the real `TriTrackApp`, and photographs
   two devices' worth of states in **one app session** — see "Two halves"
   below.
5. `driver.dart`, on the host, writes each image into `build/screenshots/`.
6. `review.dart` compares the new images against the committed ones and
   **stops**.

## A harness must be assembled from the app's configuration (`/w-10`)

`harness.dart` builds a `ProviderContainer` and pumps the real `TriTrackApp`
into it. Until 2026-09-03 that container was built **with no `retry:`**, so it
ran Riverpod's default retry policy — ten attempts over 38.2 seconds — where
`main.dart` runs `appRetryPolicy` and gives up in under two.

**That published a wrong picture and cost a task.** On a device with no server
the project Members screen's two server-backed sections fail immediately; under
the app's policy their explanation is on screen in about 1.6 seconds, and under
Riverpod's default they spin for twenty. `/w-11` saw the twenty seconds,
concluded the providers *never resolve*, wrote that into a readiness comment and
filed it as an app defect — and `project-members.png` went onto the site showing
a state a person on a phone never sees for more than a couple of seconds. Task
11.142 went looking for two stuck spinners and found this file.

**The general rule, which is why `preflight.dart` exists rather than a fixed
line:** anything a harness assembles for itself that the app also assembles must
be assembled the app's way, or everything the harness observes is evidence about
the harness. `test/documentation/retry_policy_applied_test.dart` asks the same
question of `lib/` and cannot see this directory — it scans for
`ProviderScope(`, which is not what a harness builds — and widening it here
would put a content-lane file into the code lane's red (task 11.118's lesson).
So the guard lives beside the harness it guards, and it is a **script rather
than a test** because `flutter test` refuses a file under `integration_test/`,
asking for a device.

## What "finished" means, and why it is not a number (`/w-11`)

**Until 2026-09-03 this harness had no idea what a finished screen was.** It
navigated, slept for a duration somebody had typed into `shots.dart`, and
fired the shutter. On 2026-09-02 the map needed longer than its 12 seconds, so
the run photographed the map, the truth-point panel and everything behind them
with *"Downloading terrain… 12/72"* across the bottom and no viewshed overlay —
**and reported "26 of 26 states photographed; no screen threw."** Nothing
failed, because "the screen had finished" was not part of what anything
asserted. A person looking at the images is what caught it, which is the same
sentence this project has now written about a suite that got 250× slower and
stayed green.

The wait was then raised to 90 seconds. That made the pictures right and left
the instrument exactly as blind: **a number raised until the pictures look
right is wrong again the next time anything changes, and wrong silently.**

So a capture now has a **question** instead of a sleep. `readiness.dart` holds
one `ReadinessCheck` per state — the map's is *the viewshed overlay is drawn
and the status bar is quiet*, the compass's is *the magnetic readout shows a
number instead of a dash*, the log's is *a seeded row is on screen and nothing
is spinning*. A check returns `null` when the state is ready and otherwise a
phrase naming **what it is still waiting for**, which is what the run prints
when it gives up.

Three things follow, and each is deliberate:

- **The remaining number is a ceiling on patience, not a duration.** A state
  ready in 900 ms is photographed at 900 ms. The ceiling only decides when to
  stop asking and record a red. Most are 20 seconds; the two map states are
  three minutes, because a simulator with an empty elevation cache really does
  spend a minute or so fetching terrain.
- **Every shutter goes through one funnel.** `shoot()` in `capture_test.dart`
  asks the condition before it calls `takeScreenshot`, so a state cannot be
  photographed without being checked — or, if it has no condition, without the
  run saying so.
- **The run prints how many states have no condition, including when that is
  zero.** A sweep without a denominator is a claim nobody can check, and a
  state added to `shots.dart` with no entry in `readiness.dart` is a shutter
  with nothing watching it.

**The 72 tiles were blamed on the wrong thing, and this is worth knowing before
the next fixture change.** `/w-09` attributed them to its richer fixture — eight
bearings on one collar instead of three. They do not depend on the fixture at
all: the map fetches the terrain disc around the *GPS fix*, sized by
`ViewshedConfig.maxRangeMeters`, a fixed 35 km, which at the seeded coordinates
is 8 tile rows × 9 tile columns = **72, whatever the seed holds**. What varies
is whether the simulator's elevation cache is warm — which item 8 of "What it
cannot photograph honestly" below had already written down a month earlier.
`/w-11` brought the fixture from eight bearings to five and the tile count did
not move, which is the plainest demonstration available that a smaller fixture
was never the fix.

### A condition that cannot pass vacuously, and the two tries it took (`/w-16`)

**The Position screen was photographed for a year with a blank map on it.** Its
condition asked three things — nothing spinning, no long computation running,
the bearings panel drawn — and all three are true within half a second of the
screen being built, long before its map pane has fetched anything. `/w-15`
measured the shot moving **16.15%** of its pixels on one run and **5.61%** on
the next with nothing in between touching it: what varied was how many basemap
tiles had arrived before the shutter. The iPad's Position map draws completely
and its diff was a stable 0.13% twice, which is what said the fault was the
capture and not the screen.

**The obvious repair is unsafe and `/w-15` said so before anybody tried it.**
`_noImagesDecoding` asks the framework whether `pendingImageCount == 0`, which
is true when every requested image has finished — **and equally true before the
first one has been requested.** Bolting it on would have passed instantly and
published the same blank map under a green readiness line.

**The first real attempt was also wrong, and the way it was wrong is the
lesson.** Counting drawn tiles against the tiles the map had asked for took the
run-to-run difference from 15.61% to **0.21%** and stopped there: two runs came
back pixel-identical and a third was short a sliver of one tile at the top
right corner. The set of `Tile` widgets is itself something the map grows — **a
tile the camera has not asked for yet is not an undrawn tile, it is not a tile
at all**, and no arithmetic over the tiles present can see the one that is
missing. A check that reads only what exists cannot notice what does not.

So `_basemapTilesDrawn` asserts **coverage**: the union of the rectangles the
drawn tiles occupy, against the rectangle `FlutterMap` occupies. Every logical
pixel of the pane has a drawn tile behind it, or the check says how many are
short and on which edge. Three consecutive runs then came back **pixel-
identical**. It has three named failures and no silent pass — no map, no tiles,
and tiles that do not reach the edges — and it prints its count on success as
well as on failure, so the denominator is in the log where somebody can watch
it change.

### The bearing-drag search widens its view rather than giving up (`/w-16`)

Adding the 6.1-inch profile found something the other two could not: **the
picture of the app's least discoverable gesture does not exist at the default
zoom on a shorter screen.** That run saw **one** bearing origin where the
6.9-inch phone sees two, and the bearing it selected pointed 346° — its tip was
off the top of a pane 112 logical pixels shorter, so flutter_map never built the
handle, and the run correctly reported that both drag images were pictures of an
ordinary map.

Nothing was wrong with the app or the fixture. So `capture_test.dart` now zooms
out a level and looks again, up to three passes, using the map's own
`MapController` — and **puts the camera back afterwards**, because
`joined-sync-indicator` in half two is another picture of the same map. A
profile that finds a candidate on the first pass never zooms, which is why the
two existing profiles' images are untouched by this: the iPad and the 6.9-inch
phone both still report *"after no zooming"*.

## The part a person cannot skip

**A regenerated screenshot that silently replaces its predecessor is not a
check.** It is the same defect one level over from a copy-drift check nobody
reads.

So `review.dart` never overwrites anything on its own. It prints, per screen,
whether the image is unchanged, changed (with how much of it moved), new, or
missing; for a changed screen it writes `<name>.diff.png` beside it with every
moved pixel painted red, so you can see *what* moved rather than only how much.
Then it exits 1 and writes nothing. Running the same command again with
`--accept` is the acknowledgement.

**It also prints `NEARLY` for a screen that moved and stayed under the
threshold**, with the number (`/w-06`). That line exists because the verdict is
a yes/no and the number behind it is what a person needs when the verdict is
wrong — see the tolerance section below, where a real change to the record
screen's position line measured 0.1069% against a 0.12% threshold and was
called unchanged.

**And `--accept` writes those screens too.** The threshold decides whether
somebody is *asked*; it is not a rule about which pictures the repository
keeps. Accepting only the screens past it leaves the committed set a patchwork
of two runs, and the ones that get stranded are exactly the sub-threshold
changes that were real content rather than noise.

Exit codes are the contract, the same shape as `website/tools/`:

| code | meaning |
| --- | --- |
| 0 | every screen matched, or `--accept` wrote the new ones |
| 1 | something changed, is new, or has disappeared, and nobody has said yes |
| 2 | the review could not run — **not a pass** |

Exit 2 covers an empty output directory, and it has already earned its place: a
version of this harness reported *"All tests passed"* while capturing nothing
at all, and the only thing that noticed was the review refusing to call an
empty directory green. It caught a third one on `/w-05`'s first run, when a
refactor made the provider overrides a `List<dynamic>` and the app never
booted.

**`/w-06` added the fourth case: a file that goes away underneath the review.**
`review.dart` caught `PngFormatException` around each read and nothing else, so
a staging file deleted between the directory listing and the read escaped as an
unhandled `PathNotFoundException`, the process exited **255**, and
`regenerate.sh` read any non-2 exit as "a screen changed and nobody has said
yes." **A run that could not read its own output reported as ordinary drift** —
worse than a crash, because a crash gets investigated and drift gets accepted.
Both ends are closed now: any filesystem error is exit 2 with a sentence saying
the file went away, and `regenerate.sh` treats an exit code that is not 0, 1 or
2 as the review crashing rather than as a verdict about the images.

**Since `/w-05` it also covers a state that has never been photographed
before.** `shots.dart` holds the list of names a complete run produces, and
both halves read it: the capture run walks it, and `review.dart` — a different
process, on the host — refuses with exit 2 if any name on it has no file.
That is the half the image comparison cannot do. A screen that *stops* being
photographed is caught below as MISSING, because its old image is still in the
repository; **a brand-new state has no predecessor**, so on the run that
introduces it there is nothing for its absence to differ from, and a state
that silently captured nothing would arrive as a complete, green set. A name
appearing twice in that list is also exit 2 rather than a last-write-wins,
because the second shot would overwrite the first's file and the review would
then report one state where two were photographed.

### Reaching something a `ListView` has not built yet (`/w-08`)

`scrollTo` in `harness.dart` is what a capture calls before photographing
something below the fold, and **it exists to be loud**: a scroll that does not
arrive is a capture error, because the shutter still fires and the picture is
of the top of a screen filed under the name of something further down.

Task 11.99 put a "Your role" card at the top of the members screen, which on
the phone pushed the pending-request section far enough down that a `ListView`
had not built it at all. `scrollTo` used `ensureVisible`, which needs a built
widget to ask *its* scrollable for a reveal, so it correctly reported that the
target was not there — and `owner-approval-sheet` came back as a picture of the
members screen, under an error saying exactly that. **The assertion did its
job.** Two things were then needed to make it stop being right:

- **Drag the list before concluding the app has lost something.** `scrollTo`
  now falls back to `scrollUntilVisible`, and a target that arrives is
  announced with a line saying it had to be dragged for — because "this screen
  has grown a section since the last run" is a fact worth reading.
- **Drag the *right* list, which is not the framework's default.**
  `scrollUntilVisible` defaults to `find.byType(Scrollable).first`, and
  `app_router.dart` is a `StatefulShellRoute.indexedStack`: **all five tabs
  stay mounted at once**, each with a scrollable of its own, underneath
  whatever route is on top. The first in the tree is the map's. The first
  attempt at this repair dragged that one, changed nothing, and reported the
  target as absent — on a real run, which is how it was found. It now drags
  the scrollable a tap could actually reach.

### `SAME`: two names, one picture

`shots.dart` already refuses a duplicate *name*, because the second shot would
overwrite the first's file and the review would report one state where two were
photographed. `/w-08` found the same lie arriving by the other door: two
different names whose images came back **byte-identical**.

On the iPad, `owner-members-and-code` and `owner-pending-request` are one
picture — the whole members screen fits on that geometry, so scrolling to the
pending request moves nothing — and **the committed pair had been identical
since the day they were written.** Nothing noticed, because nothing was
looking. The review now prints a `SAME` line naming every such group.

**It prints rather than failing**, for the same reason `NEARLY` does. Whether
two states collapse into one picture is a fact about a device's geometry and
can be legitimate: the iPad set exists for App Store submission, where a
duplicate wastes a slot rather than misleading a reader, and the guide's pages
use the phone images. A hard failure would force a manifest redesign on
whoever next regenerates, on a profile no page uses. **So the instrument says
what it found and a person decides** — and on the phone, after the scroll
repair above, it finds nothing to say.

## Two halves, in one app session, in this order

**Half one: no server configured.** The app's default and fully supported
state (task 10.2), and the thirteen screens `/w-02` first committed. A device
with no server shows no sync surface at all, so this half has to come first —
the moment a server address exists, every screen above gains something and
every one of those images moves. **That was a coloured strip until task
11.189 and is a dot on the More tab since** (`/w-14`); the More tab is in the
navigation bar of every screen in the shell, so the sentence survives the
redesign.

**Half two: configured, signed in, and joining a project** (`/w-05`). The
guide's flagship section is joining a project, and a page explaining how to
join illustrated by a device that never joined one is worse than a page with
no pictures. `joined.dart` drives the app's own `FakeSyncTransport` — the one
every client sync test already runs against — through a whole join: a code
typed in, the request sent, the owner approving on their own device, the
download held open long enough to photograph, and the project arriving. It
also gives the owner's side a join code, three members with all three roles,
and one stranger waiting for approval.

**No server is started, and nothing reaches the network.** A real server would
make every image depend on what some machine happened to be holding that
afternoon. Three seams are replaced, all of them ones the app's own tests
already replace, and each is inert until the second half begins.

**The middle one used to be `membershipTransportProvider` and is now
`serverTransportProvider`** (`/w-10`). Task 11.97 gave the app **one**
construction of a connection to its server, so the narrower seam is now a
single line forwarding to the wider one, and `ProjectLinkController` — which
this file previously carried a subclass of, because it built its own transport
— reads the same provider. The subclass is gone; every join in the run is the
app's own controller.

**Which means the old sentence here, that the sync engine is never faked and
never run, is no longer true of the whole run**, and a claim true of some
captures and false of others is worse than a stale one. The table at the top of
`joined.dart` says it per capture. In short: everything up to
`joined-sync-status` is drawn from the local database and the durable sync
bookkeeping with no round run at all, and the four `sync-` captures at the end
each run one real `SyncEngine` round against the in-memory server. Nothing
reaches the network in either case — that used to be guaranteed by the engine
never running, and is now guaranteed by its only connection being an in-memory
object. The last-attempt stamp is still set so the app's own foreground sync
finds nothing due mid-run.

### Four screens that print words where they printed tokens (`/w-10`)

Task 11.199 stopped four surfaces printing a storage spelling at a biologist —
`directional`, `omnidirectional`, `regular_pulse`, `lost` — and **no picture had
ever existed of any of the four.** That is not the same as four pictures that
came back unchanged: with no baseline the comparison cannot say a screen did not
move, it can only fail to look at it, and `review.dart`'s MISSING check cannot
see it either because a state nothing captures is a state nothing misses.

They are `paste-preview`, `project-tags`, `log-supersede` and
`tag-details-readonly`. The first three are in half one, immediately after the
route loop, because all three are More-tab screens reached by a route and a tap
or two and none of them touches the map. The fourth needs a project this device
does **not** own, so it sits in half two beside `project-tags-viewer`.

**`project-tags` was `project-setup-tags` until `/w-13` (2026-09-18)**, when
task 11.245 moved a project's tags off Project Setup onto their own screen,
`More → Tags`. The old name described a screen that no longer exists.

**Two of them needed the fixture to grow, and both additions are named where
they are made.** `seed-obs-juniper-omni` is a record with no bearing, because a
supersede candidate without one is labelled by its record *type* and every
observation in this fixture was directional — a picture of the picker would
otherwise have covered the changed line with nothing at all. And the paste
screen's payload is built by the app's own `buildTriTrackClipboardPayload`, the
function the Log screen's *Share observation…* calls, so the preview card cannot
be a picture of a format nothing in the app produces.

**Two finder bugs and one app defect came out of their first run**, which is
the argument for taking pictures of a screen nobody has photographed. Two rows
in this app put a name and a number in one `Text`, so `find.text('Ridgeline')`
and `find.text('East Rim')` matched nothing and both states were photographed
as the screens behind them; and the supersede picker truncates the field that
distinguishes one candidate from another (item 12 below). A fifth state was
attempted in the same task and abandoned with its measurements written down —
item 11.

### The three truth-point states sit at the end of half one (`/w-07`)

`record-truth`, `truth-point-panel` and `truth-point-edit` are reached by taps
rather than by routes — a segment on the record screen, a point tapped on the
map, and a modal over that — so they live after the route loop instead of in
`shots`. They are in **half one**, on the unconfigured device, because nothing
about a truth point needs a server, and a sync surface on two of the section's
three pictures and not the third reads as an inconsistency in the app rather
than as two devices.

**Two things that run does which are not obvious, and both are load-bearing.**

- **It puts the record screen's tab back to Directional afterwards, and checks
  that it went.** The draft autosaves and outlives the test, so a screen left
  on Truth is state every later capture inherits. It was written when
  `joined-sync-bar` re-photographed `/record` under a server; that shot is
  `joined-sync-indicator` and is of the map since `/w-14`, and the check is
  kept because "nothing photographs this screen today" is exactly the
  assumption a future shot falsifies without saying so.
- **It taps the truth-point marker where the marker is drawn, and says whether
  that worked.** This began as the measurement of a defect: the marker was
  anchored so that its little square sat about 28 logical pixels *above* the
  position it stood for, while the map's own hit test measured from the
  position and accepted 24 — so tapping the thing you could see selected
  nothing. `/w-07` found it by trying to write the sentence "tap the truth
  point", filed it for the code stream rather than fixing it here, and made
  the run print *opened* or *did NOT open* on every capture instead of
  asserting a reading of the code.

  **Task 11.100 fixed it and this line is what announced it**, printing
  *opened* for the first time on 2026-08-31, on both profiles. **The
  measurement stays** — it is now the thing that would notice the anchor
  regressing, and it costs one tap. `/w-08` corrected the geometry it prints
  along with the fix: the square is now centred on the coordinate, so the
  bottom of the marker's box is 20 pixels below the point rather than on it,
  and a line still calling that "the coordinate" would be this harness
  describing a mechanism the code no longer has.

**The images the guide should use for the join flow are the `join-`, `joined-`
and `owner-` ones.** The unconfigured `join-project` image was deleted by
`/w-05`: on a device with no server there is no control anywhere that opens
that route, so it was a picture of a screen nobody can reach, showing the
words *"Could not load projects: SyncTransportException(not_configured)"*.

## The tolerance, and what it costs

A pixel counts as moved when any colour channel differs by more than
**12 / 255**. A screen counts as changed when more than **0.12%** of its pixels
have moved — about 4,500 pixels out of 3.8 million on a 6.9-inch iPhone.

Both numbers are measured, not chosen. Two consecutive runs of the same commit
on this machine left **twelve of the fourteen screens pixel-identical**. The
two that moved:

- `checklist`, **0.051%** — it prints how many map tiles are cached, and that
  depends on how many the map run happened to fetch. This is real varying
  content, not rendering noise.
- `project-members`, **0.013%**.

0.12% sits about twice above the worst of those.

**`/w-05` re-measured it against the ten new states and did not need to move
it, and `/w-03` did not either.** Two consecutive runs of both profiles on the
same commit came back **23 of 23 unchanged, on both** — including
`join-downloading`, which shows a spinning progress indicator mid-rotation.
`/w-03` added a twenty-fourth state and saw the same: the two screens that did
move, moved because the app had changed under it (see item 1 below), and moved
by the same fraction on two separate runs. That one reproduces because the
download is held open by the harness and released on the capture loop's own
fixed clock, not because a spinner is stable.

### Re-measured with the GPS fix on (`/w-06`), and the headroom is thinner

Switching the fix on gave the map a computed viewshed, which is the most
elaborate thing this harness draws, so it was measured again rather than
assumed. Two consecutive `iphone-6.9` runs on the same commit:

- **20 of 23 images byte-identical**, `map` among them. The viewshed
  reproduces.
- `record` and `joined-sync-bar` (now `joined-sync-indicator`) differed as files but **0.0000% of pixels
  moved** — encoder-level noise below the per-channel tolerance.
- `project-members`, **0.068%**: two progress indicators, on the join-code and
  waiting-to-join sections of a device with no server, caught at different
  points of their rotation. Up from the 0.013% measured in August, and this is
  the harness's real noise floor.

**And in the same run, a real change measured 0.1069%** — the record screen's
position line going from *acquiring* to a coordinate, which is arguably the
single most guide-relevant line in the app. So on this harness the noise floor
sits at about 0.07% and a genuine one-line change sits at about 0.11%, and
**the threshold cannot reliably separate them.** Lowering it to catch the
record line would make `project-members` red on every run, which is the failure
the tolerance exists to avoid. That is why `NEARLY` was added instead: the
instrument reports the number and a person decides, rather than the instrument
deciding wrongly and saying nothing.

**What that costs, stated rather than implied.** A word of body text at this
scale is roughly 150 x 40 pixels — about **0.16%** of the screen. So a single
changed word is only *just* above the threshold, and a shorter word, or one in
a smaller type size, can slip under it entirely. A changed heading, a moved
control, or anything the eye would notice at a glance is far above it and will
be reported. **A single short word, changed in place, may not be.**

The copy-drift check in `website/tools/` is what covers that case — it asks
whether the app still contains a quoted string, which is exactly the question a
pixel comparison cannot answer. Between them they catch more than either does
alone, and **neither is a guarantee on its own**.

A comparison so strict that every run is red teaches people to click through,
which is worse than no comparison at all. That is the trade being made.

### One screen that does not reproduce, and it is the iPad's (`/w-08`)

`truth-point-edit` on `ipad-13` came back **11.64% different between two
consecutive runs of the same commit**, which is a hundred times the noise floor
measured above. It is worth being precise about what moved, because the number
on its own would send somebody hunting the wrong thing:

**The dialog is identical. The map behind it is not.** The modal sits about
fifteen logical pixels lower in one run than the other, and the map visible
around it is panned to a different place — so almost all of those pixels are
background. The likeliest cause, and it is a reading rather than a measurement:
the precision field opens focused, the simulator raised a software-keyboard
affordance in one run and not the other, and the changed view insets moved both
the centred dialog and the map's camera.

**Neither picture is wrong**, which is why this is written down rather than
fixed. `/w-08` accepted the one it looked at and left it there. The phone's
`truth-point-edit` is stable — it moved 0.0108% across the same two runs, and
the phone came back **26 of 26 byte-identical** — and the phone is the image
every guide page uses, because `{{< shot >}}` defaults to `iphone-6.9`. The
iPad copy exists for App Store submission.

**What to do when a run flags it.** Look at it; if only the map behind the
dialog has moved, it is this. Do not lower the tolerance to catch it and do not
raise the tolerance to hide it — 11.64% is far above anything a threshold
should be asked to absorb, and a threshold wide enough for this would be wide
enough for a changed heading.

### The 6.1-inch profile, and why the device is an iPhone 16 (`/w-16`)

`phoneSize` in `test/support/app_shell_harness.dart` is **393 × 852**, and
essentially every layout assertion this project has — the clear-band floors,
`BudgetedColumn`, the wrap guards, the disabled-reason geometry — is written
against it. Until `/w-16` the harness photographed **nothing** that size. Tasks
11.193 and 11.195 were both about a control cut off on a 6.1-inch phone and
neither could be checked against a picture.

**The obvious device was wrong and it was measured rather than assumed.** An
iPhone 17e is the 6.1-inch phone in the current line-up and is what task 11.195
used by hand; it photographs at **1170 × 2532, which is 390 × 844** — three
points narrower and eight shorter. A profile whose entire justification is
"exactly the geometry the assertions use" cannot be approximately that, so the
device is an **iPhone 16**, which is 393 × 852. `regenerate.sh` creates that
simulator if the machine does not have one, because a profile that only works
where somebody remembered to add a device by hand is a profile that quietly
stops being captured.

### Why the 6.1-inch profile shoots everything

**Every state, on all three profiles.** A subset was considered — "only the
screens with measured floors" — and rejected, for four reasons in descending
order of weight.

1. **A subset is a hand-maintained list of where defects are expected, and this
   project has measured that list being wrong.** Task 11.126 pumped two screens
   at real phone geometry for the first time and found **three live overflows in
   the first run**, on widgets nobody had suspected, including a "Paste from
   clipboard" button that had been cut off on every phone since it was written.
   None was a regression. The screens with written budgets are the screens
   somebody already thought about; the value of a new profile is concentrated in
   the ones nobody did.
2. **The saving is small, because the cost is not per image.** A full 34-state
   profile run is **3m 44s to 4m 20s** warm on this machine, and the two longest
   waits in it — the map's cold terrain fetch and the join sequence — are single
   states a "screens with floors" subset would still have to include. Skipping
   two thirds of the shutter presses would save well under a minute.
3. **A subset needs machinery that does not exist, and the machinery is the
   dangerous kind.** `shots.dart` publishes one list and `review.dart` refuses
   any run that does not produce all of it — which is what makes a silently
   skipped state impossible. A per-profile subset means teaching both halves to
   tell *deliberately not photographed* from *quietly missing*, which is exactly
   the distinction this directory exists to keep.
4. **Review attention is a real cost and it is paid once.** Thirty-four new
   baselines had to be looked at on the first run. After that the review only
   asks about screens that moved, and an unchanged screen costs nothing.

The disk cost is **6.6 MB**, against 7.4 and 7.8 for the two existing profiles.

**No macOS.** `flutter drive -d macos` builds and runs the app fine, and then
`takeScreenshot` fails with "No implementation found for method
captureScreenshot": the `integration_test` plugin does not implement it on
macOS. Capturing the desktop app needs a different mechanism — `screencapture`
on the host, driven from `driver.dart`. Until somebody builds that, there are
no desktop screenshots rather than hand-taken ones.

**No Android.** Task 11.66 has not been run; there is no point illustrating a
platform nobody has started.

## The compass: the sensor is faked, deliberately

A simulator has no magnetometer, so the compass screen is the one surface it
cannot honestly show on its own. There were two options and **this harness
fakes the heading at the app layer**, exactly as it already does the position
stream — `compassHeadingProvider` is overridden with 47° — **a variable since `/w-32`**, held at 47 for every picture except while *Take on map*'s sweep is being scripted, and put back afterwards.

The alternative was one hand-taken photograph of that screen. It was rejected
because it contradicts the rule this whole directory exists to enforce: **a
photograph cannot be regenerated.** The compass screen would be the only image
on the site that silently rots when the screen changes, and it would be the one
nobody remembered to re-take.

What is faked is one number. The layout, the type, the bubble level, the
declination arithmetic and everything else on that screen are the real app.
**The guide must say the heading shown is illustrative**, because it is.

## One run at a time, and the script enforces it

`regenerate.sh` empties `build/screenshots/<profile>` when it starts that
profile, and until `/w-06` there was nothing stopping a second run from doing
that while the first was between writing its images and reviewing them. **It
happened on 2026-08-31**, from two windows on one working tree: 23 files were
removed after the driver wrote them, and `review.dart` died with a
`PathNotFoundException` stack trace rather than exiting 2 — so `regenerate.sh`,
which treated any non-2 exit as "a screen changed", reported a run that could
not read its own output as ordinary drift.

**The enforcement is in the script rather than in a document, and that was the
point.** A rule saying "do not run the harness" cannot compete with a good
reason to run it: the run that destroyed those images was a code task checking
that its own map fix worked, which is a reasonable thing to want to do. So the
script takes a lock — `build/screenshots/.regenerate.lock`, created with
`mkdir` because `mkdir` is atomic and there is no portable `flock` on macOS —
before it deletes anything, and a second run **refuses to start**, exits 2, and
prints which process holds it and when that run began.

A lock whose owning process is no longer alive is reclaimed, loudly: a crashed
run that left the harness permanently unusable would be a worse failure than
the one the lock prevents, and a silent reclaim would be a lock that only
pretends to be one.

Watched on 2026-08-31: a second run started against a live first one refused
with exit 2 and deleted nothing, and a run whose staging directory was removed
under it during the review exited 2 with a sentence naming the file.

**Both of the "harness said nothing was wrong" incidents behind this list were
caught by the same thing** — `review.dart` refusing to call an empty output
directory a pass. `flutter drive` printed "All tests passed" over zero
screenshots twice, once when the capture loop was silently detached and once on
macOS where the screenshot method does not exist. Exit 2 is not decoration.

## The data in the pictures

`seed.dart` and `joined.dart`, and **every bit of it is invented**: four people
at `example.org`, three collars with made-up frequencies, two projects, and a
study area in the Owyhee uplands of south-eastern Oregon chosen for having
nothing to do with anybody's field site. **A published screenshot of a real collar location is a disclosure of
where an animal is, not a picture of an app** — so the seed is deliberately
somewhere else, and deliberately not where this project's people work.

**The join screens raised the stakes on that rule, and `/w-05` says so out
loud.** An owner approves somebody by their **email address** — it is the one
thing about a stranger the server can vouch for, and it is printed on screen.
So a careless fixture here would publish a real person's address, not merely a
real name. `example.org` is a reserved documentation domain and can never
belong to anybody, which is why every address in both files is at it.

Timestamps are fixed. A harness whose output changes because the clock moved
cannot answer the only question it exists to answer. That is also why the
"last synced" stamp on the sync status screen reads *"Synced on 2026-02-11"*
rather than
*"just now"*: a device that has genuinely just synced says "just now" and then
says "1 min ago", and the status screen prints an absolute timestamp that
would differ on every single regeneration. A screenshot that reports a
difference every time trains people to accept differences.

## What `/w-32` added: scripted taps, a scripted compass, and a video

**Thirteen new states (52 in the manifest now), all in this one run, none needing a server or a sign-in.**
The in-memory fake server already modeled deletion (a scheduled deletion, a
destroyed project, the *deleted but still on the server* list, a restore), so
**nothing was added under `test/`**.

- **The Position sheets** (`position-cautions`, `position-legend`,
  `position-past-estimates`): one tap each on the screen the route loop already
  photographs. Nothing is saved.
- **Link a tag and Quick add** (`link-tag-picker`, `link-tag-confirm`,
  `quick-add`, `quick-add-review`). Every seeded tag is already worn by an
  animal and every library entry is already on the project, so the picker would
  offer only *New tag...*. The run writes **an animal with no collar and a
  library-only tag**, photographs both flows to the screen that asks, backs out
  of them, and **hard-deletes** the two rows. Hard, not the app's soft delete: a
  tombstone is a row the next sync round would push, and the sync-status
  pictures later in the run count rows waiting to be sent. *The date on the date
  card is the day the run was made*, because the app reads `DateTime.now()`.
- **Take on map** (`take-on-map`, `take-on-map-released`) is driven by
  `take_on_map.dart`. A simulator has no compass and the button hides without
  one, so `harness.dart`'s compass reads a variable (`setFakeHeading`) that the
  script moves: it sets the heading, presses the hold button with
  `tester.startGesture`, turns the phone from 31 to 65 degrees while it is down,
  and lets go. *Today's earlier bearings* are two directional bearings on Sage
  written for the run with timestamps seconds ago (the seed's are fixed in
  February and are not "today" to this screen), **aimed from computed positions
  at one spot**, and hard-deleted afterwards. The compass is put back to 47 and
  the Record draft to the tag it had.
- **Deleting a project** (`delete-project-dialog`, `projects-countdown`,
  `projects-deleted-section`, `sync-project-deleted`). The dialog is reached
  through the row's three-dot menu; *Schedule delete* is really pressed, so the
  countdown row is drawn from the notice the app wrote itself, and the schedule
  is then withdrawn on the fake server. *The countdown date is the run's day
  plus the server's waiting period.* `sync-project-deleted` is Steens, the
  project the device joined earlier in the run (`openProjectForRound`): the fake
  destroys it and one real round meets the refusal.

**Three smaller changes from task 11.319.** After the Map tab opens with a GPS
fix the first frame is drawn at the opening zoom and the camera then moves, so
`awaitCameraSettled` (in `map_framing.dart`) waits for four consecutive 250 ms
looks at the same center, zoom and rotation before a marker is found and tapped.
The `truth-point-panel` readiness check finds the card by its widget
(`_SelectionInfoPanel`) as well as its title, so a marker label can never
satisfy it. And the run prints one `SCREENSHOT HARNESS: capturing <name>` line
per picture, so a long run shows how far it has got.

**A new block can no longer end the run.** The new tap-driven blocks run
through `guarded`, which records a thrown error against the block and pops any
modal it left open. Before that, one finder that matched nothing ended the whole
test body and 24 states were reported never photographed behind it.

### The pilot video, and how it is regenerated

`record_video.sh` boots the iPhone 17 Pro Max simulator, runs `video_test.dart`
(the same Take on map script, with the compass turned continuously instead of in
steps), starts `xcrun simctl io <device> recordVideo` when the test prints
`VIDEO_START` and stops it on `VIDEO_STOP`, so the clip is the sweep and not the
app booting. `retime_video.swift` then plays it back four times faster as a
muted 60 fps MP4 (Apple's AVFoundation; there is no ffmpeg here). **It writes
the file and commits nothing.**

**Why the test draws every frame while it records.** The test binding normally
draws only the frames a test pumps, and `settle` pumps every 120 ms, so the
first recording was 7.4 frames a second and looked choppy at 4x. `video_test.dart`
switches the binding to `fullyLive` between `VIDEO_START` and `VIDEO_STOP`, which
took the recording to about 45 frames a second (2026-10-01). The still first frame for readers who do not play it is the
`take-on-map` picture itself, which the clip begins on, so the poster is
regenerated with everything else. When the screen changes, run the script again.
